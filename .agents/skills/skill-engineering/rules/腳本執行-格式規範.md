# Rule 1 - 一律用 `uv run` 執行腳本

- Level: `MUST`
- 腳本一律以 `uv run <腳本絕對路徑> <參數>` 執行；uv 會讀取腳本的 PEP 723 區塊，自動建立隔離環境、安裝相依套件，必要時下載符合 `requires-python` 的 Python
- 有 uv 時，不用 `python3`、`py`、`pip` 這類名稱來執行腳本或安裝套件，它們在不同平臺、不同機器上指向的對象不一樣
- 只有同時符合兩個條件時，才可以不用 uv 而改用 `python`：找不到 uv，且腳本的 `dependencies` 是空清單；此時依序嘗試 `python3`、`python`、`py -3`，採用第一個 `--version` 成功、且版本符合 `requires-python` 的

## Good Example

- 用 uv 執行，由 uv 決定 Python 與環境

```bash
uv run "D:/AIBDD/practise/.claude/skills/skill-api-doc/scripts/check_error_codes.py" "D:/proj/docs/errors.md"
```

## Bad Example

- `pip` 與 `python` 可能屬於不同的 Python（例如 pip 是 3.10、python 是 3.13），套件裝到另一個環境；`python3` 在 Windows 也可能只是 Microsoft Store 的殼

```bash
pip install pyyaml
python3 scripts/check_error_codes.py docs/errors.md
```

# Rule 2 - 以 skill 目錄展開成絕對路徑，不 `cd`

- Level: `MUST`
- SOP 裡的腳本路徑相對於 skill 目錄，例如 `scripts/check_error_codes.py`；執行前先展開成絕對路徑
- skill 目錄是放著 `SKILL.md` 的目錄（Claude Code 稱為 `${CLAUDE_SKILL_DIR}`）
- 不為了執行腳本而 `cd` 進 skill 目錄；工作目錄留在使用者的專案，傳給腳本的目標路徑也用絕對路徑
- 路徑含空格時加雙引號

## Good Example

- 腳本與目標檔案都是絕對路徑，路徑含空格的部分加了雙引號，工作目錄不變

```bash
uv run "D:/AIBDD/practise/.claude/skills/skill-api-doc/scripts/check_error_codes.py" "D:/My Projects/docs/errors.md"
```

## Bad Example

- 用相對路徑；執行時的工作目錄是使用者的專案，找不到腳本

```bash
uv run scripts/check_error_codes.py docs/errors.md
```

- `cd` 之後工作目錄改變，相對的目標路徑與後續指令都跟著失效

```bash
cd .claude/skills/skill-api-doc && uv run scripts/check_error_codes.py ../../../docs/errors.md
```

# Rule 3 - 找不到 uv 時先詢問使用者

- Level: `MUST`
- 找不到 `uv`，而腳本有第三方套件時，先停下來，向使用者說明並取得同意，才可以安裝 uv
- 提供對應平臺的安裝指令讓使用者選擇：Windows 用 `winget install --id=astral-sh.uv -e`，macOS 用 `brew install uv`，Linux 用 `curl -LsSf https://astral.sh/uv/install.sh | sh`，已有 pipx 的任何平臺用 `pipx install uv`
- 不為了繞過 uv，把套件用 `pip install` 裝進系統 Python；Debian 系等發行版的系統 Python 會直接拒絕（PEP 668）
- 安裝後 `uv --version` 仍找不到，多半是 PATH 尚未更新；請使用者重新開啟終端機，不要重複安裝

## Good Example

- 先說明原因、列出選項，等使用者同意

```text
ASK：這個腳本需要 uv 才能自動安裝相依套件，但這台機器找不到 uv。
可選的安裝方式：
- Windows：winget install --id=astral-sh.uv -e
- macOS：brew install uv
- Linux：curl -LsSf https://astral.sh/uv/install.sh | sh
是否同意由我安裝？
```

## Bad Example

- 沒有詢問就改用 pip 把套件裝進系統 Python，還加上 `--break-system-packages` 強行繞過保護

```bash
python -m pip install --break-system-packages pyyaml
```

# Rule 4 - 依退出碼處理結果

- Level: `MUST`
- `0`：成功，讀取 stdout 的結果，進入下一個 step
- `1`：腳本正常跑完但發現問題；依 stdout 的問題清單修正後重新執行腳本，直到退出碼為 0
- `2`：腳本無法執行；讀取 stderr 的說明處理（補參數、補檔案、改用 `uv run` 等），不要把它當成「發現問題」去修改產出
- 其他退出碼，或沒有任何說明的失敗：停止並回報使用者，附上完整的 stderr，不自行猜測

## Good Example

- 退出碼 1，依問題清單補上缺的欄位後重跑

```text
退出碼 1
stdout：{"violations": [{"rule": "Rule 3", "problem": "缺少 Level 欄位"}]}
→ 補上 Rule 3 的 Level 欄位，重新執行，直到退出碼為 0
```

## Bad Example

- 退出碼 2 是「找不到檔案」，卻被當成違規，開始改寫 RuleFile

```text
退出碼 2
stderr：[無法執行] 找不到檔案 rules/實作-格式規範.md
→ 把它當成違規，開始改寫 RuleFile 的內容
```

# Rule 5 - 先執行腳本，不先閱讀原始碼

- Level: `SHOULD`
- 腳本是用來執行的，不是用來閱讀的；先執行，不要先把原始碼讀進上下文
- 用法不明時，執行 `--help`；`--help` 是腳本介面的唯一說明
- 只有在除錯腳本本身時，才閱讀原始碼

## Good Example

- 用法不明，先看 `--help`

```bash
uv run "D:/AIBDD/practise/.claude/skills/skill-api-doc/scripts/check_error_codes.py" --help
```

## Bad Example

- 先把整支腳本讀進上下文，再自己推測要傳什麼參數

```text
READ scripts/check_error_codes.py 全文，再決定要傳什麼參數
```
