# Rule 1 - 施工紀錄資料夾的位置與命名

- Level: `MUST`
- 施工紀錄放在 skills 根目錄的上一層的 `engineering-runs/` 底下，本專案為 `.claude/engineering-runs/`
- skills 根目錄預設是 skill-engineering 自己所在目錄的上一層；目標 skill 在別的 skills 目錄（例如使用者層級的 `~/.claude/skills`）時，以那個目錄為 skills 根目錄，施工紀錄根目錄也換成它上一層的 `engineering-runs/`，並以新的根目錄重新執行盤點
- 施工紀錄根目錄不存在時，盤點視為沒有任何紀錄，Phase 4 建立施工紀錄資料夾時一併建立
- 不放進任何 skill 目錄，避免被當成 skill 的部位檔，也避免 skill 被刪除時紀錄跟著消失
- 每次施工建立一個子資料夾，命名為 `<yyyyMMdd-HHmm>-<主要目標 skill 名稱>`，時間用本機時間；有多個目標 skill 時用第一個，其餘寫在藍圖
- 閘門 1 指 Phase 2 的診斷單確認，閘門 2 指 Phase 3 的藍圖確認；施工紀錄資料夾在閘門 2 通過後才建立，閘門之前的診斷單與藍圖只在對話中，閘門 2 通過前不寫入任何檔案（腳本 `--output` 的暫存檔放系統暫存區，不算），也不改動任何 skill

## Good Example

- 放在 skills 根目錄的上一層，以時間與目標 skill 命名

```text
.claude/
├── skills/
│   └── release-notes/
└── engineering-runs/
    └── 20261025-1430-release-notes/
```

## Bad Example

- 放進被施工的 skill 目錄，優化時會被當成部位檔；資料夾名稱沒有時間與目標

```text
.claude/skills/release-notes/runs/run1/
```

# Rule 2 - 施工紀錄資料夾的內容與還原點

- Level: `MUST`
- `blueprint.md`：閘門 2 通過的藍圖，狀態欄隨施工更新，兼作進度
- `diagnosis.md`：優化時存入閘門 1 通過的診斷單，新建沒有
- `baseline/<skill 名稱>/`：優化時為藍圖處置列涉及的每個 skill 複製整個目錄，作為還原點與複雜度基準，新建沒有
- `report.md`：Phase 6 的完工報告
- 還原時以 `baseline/<skill 名稱>/` 整個目錄取代現有目錄，先刪除現有目錄再複製，不逐檔還原
- 設計落差重做時沿用同一個資料夾，只覆寫 `blueprint.md` 與優化才有的 `diagnosis.md`，不重新複製 baseline，否則第一輪施工前的原樣會被蓋掉
- blueprint.md 的狀態欄由 skill-engineering 在每次核對通過後立即改寫並存回，不另立 SOP step
- 不放其他檔案，暫存檔放系統暫存區

## Good Example

- 優化時四種內容都有，baseline 以 skill 為單位保存整個目錄

```text
20261025-1430-release-notes/
├── blueprint.md
├── diagnosis.md
├── baseline/
│   ├── collect-changes/
│   └── release-notes/
└── report.md
```

## Bad Example

- baseline 只複製被改到的檔案，還原時新增的檔案不會被清除，也算不出完整的複雜度基準

```text
20261025-1430-release-notes/
└── baseline/
    └── release-notes/
        └── SKILL.md
```

# Rule 3 - 新建時建立 SKILL.md 外殼

- Level: `MUST`
- 外殼在 `<skills 根目錄>/<skill 名稱>/SKILL.md`，內容只有 frontmatter 與空的 `# SOP`
- `name` 與資料夾同名，使用 kebab-case 小寫英文；`description` 取藍圖處置表 `<skill 名稱>/SKILL.md#description` 那一列的內容（已在閘門 2 校正），寫法依選型規範的 description 規定；外殼寫入後，把該列的狀態改為已完成
- 目標資料夾已存在時分兩種：是本次施工紀錄已建立的外殼（設計落差重做藍圖時），沿用，不重建；是既有的 skill 時停止施工，回到 Phase 1 改以優化處理並從 Phase 2 開始，不覆寫既有的 skill
- 不預先建立空的 `rules/`、`templates/`、`scripts/`，由 derive skill 在展開時建立

## Good Example

- 只有 frontmatter 與空的 SOP，description 寫出觸發情境與分界

```md
---
name: release-notes
description: 當要整理某個版本的發版說明時使用，例如「整理 v2.3 的發版說明」。產出依破壞性變更、功能、修正分段的發版說明。只要列出 commit 清單請改用 collect-changes。
---

# SOP
```

## Bad Example

- 目標資料夾已存在，仍直接覆寫成空外殼，既有的 skill 就此消失

```text
.claude/skills/release-notes/ 已存在 → 直接覆寫 SKILL.md 為空外殼
```

# Rule 4 - 逐列施工的順序與定位

- Level: `MUST`
- 依藍圖處置表中各列在 SOP 的位置由前往後施工，一次只施工一列，取回並核對後才進入下一列
- 同一個 step 同時有多個部位時，依腳本、規則、樣板的順序施工，腳本會把 step 拆開，規則與樣板接在拆開後留給 AI 的 step 上；前一列施工完，把後續列交付單的 step 原文改成 SOP 的實際原文
- 以交付單的 step 原文逐字定位目標 step，不用步號，因為前面的列施工會插入 READ step，步號會位移
- 委派對象依處置與部位決定：新增腳本、規則、樣板分別委派 /skill-derive-script、/skill-derive-rule、/skill-derive-template；改寫既有的腳本、規則、樣板分別委派 /skill-form-script、/skill-form-rule、/skill-form-template，在既有部位檔內新增或刪除單條也算改寫該檔；全域規則同樣委派 /skill-derive-rule，以第一個用到它的 step 展開，其他 step 只用名稱稱呼它
- 目標 skill 本身是 derive 或 form skill，或是 skill-engineering 自己時，改它的列排在所有需要委派它的列之後；SOP 列在 Phase 4、部位列在 Phase 5，排不出這個先後時拆成兩次施工，先做需要委派它的列；施工途中沿用已載入的規範，不重新讀取改到一半的檔案
- 同一個檔案有多列時合併成一次委派，交付單逐條列出；規則以標題而非編號定位，因為刪除或合併後編號會位移
- 不經委派的列：位置為 SKILL.md 內 step 的列，已在 Phase 4 由 /skill-form-sop 完成；整份部位檔的刪除列與位置為 frontmatter 的列（新建的 description 列已隨外殼在 Phase 4 完成），由 Phase 5 的刪除與 frontmatter 步驟處理；檔內單條的刪除列照改寫處理；狀態為無需施工的列不施工
- 不經委派的列完成後，同樣由 skill-engineering 把狀態改為已完成並存回 `blueprint.md`：SOP 的列在 Phase 4 核對一致後，刪除與 frontmatter 的列在 Phase 5 完成後

## Good Example

- 由前往後逐列施工，以 step 原文定位，委派對象依處置決定

```text
1. collect-changes/scripts/list_commits.py（改寫）→ /skill-form-script
2. collect-changes/rules/破壞性變更-規範.md（新增）→ /skill-derive-rule，以交付單的 step 原文「WRITE 依類型分組輸出變更清單，標出破壞性變更」定位
```

## Bad Example

- 用步號定位；前面的列已在同一個 Phase 插入了 READ step，步號位移，指到的已經是別的 step

```text
2. collect-changes/rules/破壞性變更-規範.md（新增）→ /skill-derive-rule，展開 Phase 2 第 2 步
```

# Rule 5 - 交付 /skill-form-sop 的主幹只落實已存在與保留的部位

- Level: `MUST`
- 每個有 SOP 變動的 skill 各委派一次，依藍圖主幹列出的先後；主幹與現行 SOP 沒有差異的 skill 不委派
- 交付內容為目標 skill 的路徑、藍圖的主幹與處置、預期，優化時另附不可退化清單與現行 SOP 原文
- 主幹中保留與改寫的部位，照藍圖標示的載入位置寫出 READ 或 DELEGATE，路徑只在第一次出現時寫出
- 主幹中新增的部位，在藍圖以（部位：新增 <路徑>）標示，在 SOP 裡保持純文字的 step，不寫載入、不寫路徑，因為檔案還不存在；等 Phase 5 該列展開時才由 derive skill 接上，新增腳本也只寫一個純文字的 step，載入執行規範與拆開留給 AI 的部分，都由 /skill-derive-script 展開時處理；新增的全域規則（多個 step 用到），第一個用到的 step 以外，其他 step 對它的稱呼（例如「依破壞性變更規範」）在 Phase 4 就寫進主幹，不等展開
- 優化時，主幹中未變動的 Phase 可在 Phase 行末標「（不變）」並省略 step，只列新增或改寫的 step
- Phase 4 核對 SOP 與藍圖主幹一致，只比 step 的動詞與描述；新增部位的載入 step 要等 Phase 5 才出現，不算不一致
- 交付單的 step 原文取自主幹的 step，不含部位標示；Phase 4 核對一致後，改成 SOP 的實際原文，並把 SOP 列的狀態改為已完成

## Good Example

- 藍圖標示格式規範為保留、破壞性變更規範為新增：前者照載入位置寫出 READ，後者在 SOP 裡仍是純文字的 step

```md
## Phase 2 -- 完成變更清單

1. READ 讀取 `rules/格式規範.md`，將其視為唯一格式規範來源。
2. WRITE 依格式規範與類型分組輸出變更清單，標出破壞性變更。
```

## Bad Example

- 破壞性變更規範還不存在，主幹卻已寫出 READ 與路徑；稽核會報懸空引用，derive skill 也不知道要在哪裡插入載入 step

```md
## Phase 2 -- 完成變更清單

1. READ 讀取 `rules/格式規範.md`，將其視為唯一格式規範來源。
2. READ 讀取 `rules/破壞性變更-規範.md`，將其視為唯一破壞性變更規範來源。
3. WRITE 依格式規範與破壞性變更規範輸出變更清單。
```

# Rule 6 - 交付單的欄位依委派對象補齊

- Level: `MUST`
- 每個要委派的列在藍圖的交付單區塊有一張交付單，包含目標 skill、委派對象、step 原文（逐字）與交付內容
- 交付內容依委派對象補齊下列欄位，缺任一項不得委派，也不能留給對方再詢問使用者
- 使用者還沒說明的欄位（例如驗收案例、第三方套件），在藍圖階段先填合理的草稿，交給使用者在閘門 2 校正，不留到施工時才問
- /skill-derive-template：樣板名稱與格式（副檔名）、骨架與範例路徑、格式需求（有現成範本時逐字附上原文）、填位符號偏好（沒有則寫「無偏好」）
- /skill-derive-rule：規範名稱與 RuleFile 檔名、要把關的事、約束該 step 的既有 RuleFile（沒有則寫「無」）、要搬移的既有規則（逐條附原文，沒有則寫「無」）、新增規則需求
- /skill-derive-script：腳本檔名、腳本職責（輸入、輸出、退出碼語意、依賴的外部指令與執行環境）、交給腳本與仍由 AI 判斷的部分、第三方套件與理由（沒有則寫「無，僅用標準庫」）、驗收案例（至少一個正例與一個反例）；沿用既有腳本時改寫成沿用的腳本名稱與傳入內容，不另建腳本
- /skill-form-rule、/skill-form-template、/skill-form-script（改寫既有部位）：現行檔案的路徑、要改的地方與原因、不可改變的部分；跨檔搬入規則時另附要搬入的規則原文；改寫腳本時另附驗收案例

## Good Example

- 委派 /skill-derive-script 的交付單，欄位齊全，step 原文逐字附上

```md
### 3 collect-changes/scripts/list_commits.py

- 目標 skill：`.claude/skills/collect-changes`
- 委派對象：/skill-derive-script
- step 原文：READ 讀取版本範圍內每個 commit 的標題與註腳
- 交付內容：腳本檔名為 `scripts/list_commits.py`；職責是輸入版本範圍（兩個 tag），輸出每個 commit 的標題與註腳（JSON，寫在 stdout），退出碼 0 成功、2 無法執行，依賴 git 與 Python 3.11 以上；腳本只列出 commit，判定是否為破壞性變更仍由 AI 處理；第三方套件：無，僅用標準庫；驗收案例：正例 v2.2..v2.3 退出碼 0 且輸出含註腳，反例不存在的 tag 退出碼 2
```

## Bad Example

- 交付內容只寫主題名，沒有 step 原文、輸入輸出、第三方套件與驗收案例，對方必須回頭詢問使用者

```md
### 3 collect-changes/scripts/list_commits.py

- 目標 skill：`.claude/skills/collect-changes`
- 委派對象：/skill-derive-script
- step 原文：讀取 commit
- 交付內容：做一支讀取 commit 的腳本
```

# Rule 7 - 每列取回後必須核對，落差依所在處補正

- Level: `MUST`
- 取回後核對四件事：預期的部位檔存在於預期的路徑；SOP 中被展開的 step 已改寫並載入該部位；該列以外的 step 與檔案沒有被改動；對該 skill 以只回報的方式執行 `audit_skill` 的結構檢查，逐項比對沒有新增的違規（施工中還有待刪的孤兒檔與尚未施工的列，退出碼不作為判斷依據）
- 委派對象依自己的規範必然附帶的變更，不算該列以外的改動，例如 /skill-derive-script 第一次展開時複製腳本執行規範並補 compatibility
- 改寫既有腳本的列，另以交付單的驗收案例依腳本執行規範實際執行，退出碼與預期一致，結果併入完工報告；每個案例寫出預期退出碼，正例優先用目標 skill 內現有的輸入，反例的檔案在系統暫存區臨時建立，驗收完刪除；新增的腳本由 /skill-derive-script 實跑並回報，不重跑
- 比對該列以外有沒有被改動時，優化以 baseline 為準；新建在每列施工前先記下目錄的檔案清單與 SKILL.md 內容，取回後比對
- 處置為刪除的部位檔，在 Phase 5 的刪除步驟之前會被稽核列為孤兒檔，這不算新增違規
- 核對通過後，把藍圖該列的狀態改為已完成，並存回施工紀錄的 `blueprint.md`
- 有落差時依落差所在處補正：部位檔在該列施工當下退回該列的委派對象，施工完成後才發現的落差委派對應的 /skill-form-*；SOP 退回 /skill-form-sop；施工紀錄、藍圖與 frontmatter 由 skill-engineering 自己改；Phase 6 稽核與核對的落差同樣依此補正，補正若要新增或改變處置列（例如補上稽核指出漏列的元素），先回到 Phase 3 的 THINK 步驟更新藍圖並取得使用者同意，不自行補列後直接施工
- 同一項補正兩次仍未解決時，停止並回報使用者，根因可能在交付單

## Good Example

- 四件事逐項核對，通過後才改狀態

```text
collect-changes/rules/破壞性變更-規範.md → 存在
collect-changes/SKILL.md Phase 2 → 已有 READ 該規範，被展開的 step 改為「依破壞性變更規範」
其他 step 與檔案 → 與 baseline 比對沒有多餘的改動
audit_skill 檢查 collect-changes → 沒有新增違規
blueprint.md 第 5 列狀態 → 已完成
```

## Bad Example

- 只看對方回報「完成了」就把狀態改成已完成，沒有核對檔案與 SOP

```text
/skill-derive-rule 回報完成 → blueprint.md 第 5 列狀態改為已完成
```

# Rule 8 - 刪除的順序

- Level: `MUST`
- 整份部位檔的刪除，順序是先在 SOP 移除對它的引用（Phase 4 的主幹已移除），再刪檔，最後以稽核確認沒有孤兒檔與懸空引用
- 整份檔案的刪除只由 skill-engineering 執行，不經 derive skill（derive 只展開不縮減）；檔內單條規則、單個 step 的刪除屬於改寫，委派 /skill-form-*
- 優化時只刪除 `baseline/` 內有複本的檔案；新建沒有 baseline，只刪除本次施工自己建立的部位檔（原本是藍圖已完成的新增列，設計落差重做時那一列已改成刪除列）
- 刪除的原因留在藍圖列的內容欄（依據欄寫「無舉證」或對應的編號），不留墓碑，例如 `.bak` 檔、`已棄用` 註記、被註解掉的 step

## Good Example

- SOP 已不引用，才刪檔；刪完以稽核確認

```text
release-notes/SKILL.md → Phase 4 已移除對 rules/舊版格式.md 的引用
刪除 release-notes/rules/舊版格式.md → baseline 內有複本
audit_skill 檢查 release-notes → 沒有孤兒檔與懸空引用
```

## Bad Example

- 檔案留下 `.bak`，SOP 的 step 被註解掉而不是刪除，稽核會出現孤兒檔

```text
release-notes/rules/舊版格式.md.bak
release-notes/SKILL.md → <!-- 3. READ 讀取 rules/舊版格式.md -->
```

# Rule 9 - frontmatter 只改藍圖列出的欄位

- Level: `MUST`
- `name` 不隨優化改名；要改名視為新建一個 skill，另開一次新建施工，舊的由使用者決定要不要刪，不在同一次施工內處理
- `description` 的內容依選型規範的 description 規定，只改藍圖列出的部分
- `compatibility` 由 /skill-derive-script 第一次展開時附帶寫入，藍圖不為它另列一列，skill-engineering 不手改
- 不新增藍圖沒有列出的欄位

## Good Example

- 只改藍圖第 5 列列出的 description，其他欄位原樣保留

```md
---
name: release-notes
description: 當要整理某個版本的發版說明或 changelog 時使用，例如「整理 v2.3 的發版說明」。產出依破壞性變更、功能、修正分段的發版說明。只要列出 commit 清單請改用 collect-changes。
compatibility: 需要 uv 與 Python 3.11 以上,各腳本的第三方套件宣告在 scripts/*.py 開頭的 PEP 723 區塊
---
```

## Bad Example

- 順手改了 name，其他 skill 與施工紀錄對它的引用全部失效；還手改了 compatibility

```md
---
name: release-notes-v2
description: 當要整理某個版本的發版說明時使用。
compatibility: 需要 uv
---
```

# Rule 10 - 接續未完成的施工

- Level: `SHOULD`
- 盤點結果列出的施工紀錄中，藍圖狀態欄還有待辦的資料夾，就是未完成的施工
- 使用者要接續時，先核對 SKILL.md 的 SOP 與藍圖的主幹一致，一致才接續
- 接續位置依第一個待辦列決定：位置是 SKILL.md 內 step 的列從 Phase 4 接續，其餘從 Phase 5 接續，已完成的列不重做
- SOP 與藍圖的主幹不一致時不接續，先回到 Phase 4 的核對步驟處理

## Good Example

- 第 3 列待辦，SOP 與藍圖主幹一致，從 Phase 5 的第 3 列接續

```text
20261025-1430-release-notes/blueprint.md → 第 1 列已完成，第 3 列待辦，第 5 列待辦
SKILL.md 的 SOP 與藍圖主幹 → 一致
接續位置 → Phase 5，從第 3 列開始
```

## Bad Example

- 沒核對 SOP 與藍圖是否一致，也重做了已完成的第 1 列

```text
20261025-1430-release-notes/blueprint.md → 第 1 列已完成，第 3 列待辦
從 Phase 2 重新開始，重做第 1 列
```

# Rule 11 - Phase 1 的詢問要補齊該模式需要的資訊

- Level: `MUST`
- 優化需要：問題發生的對話（沒有失敗的對話時改問一個代表案例，使用者給不出時由診斷構造，不再追問）、預期的結果、使用者認為的原因、目標 skill 與它所在的 skills 目錄
- 新建需要：用途與觸發情境、預期產出、一句真實的使用輸入、手上素材、要放在哪個 skills 目錄
- 已說明的不再問；預期說得模糊時，依預期的寫法先擬一個樣子請使用者校正
- 使用者已指明要改哪個 step 或部位檔、也說得出要改成什麼時，說明這屬於 skill-derive-* 或 skill-form-*，使用者仍要走完整流程才繼續；只說結果不對、說不出該改哪裡的，走優化的診斷，不算單一 step 或部位
- 盤點顯示有與目標 skill 相關的未完成施工時，問是否接續（依接續的規則）
- 新建且盤點顯示職責重疊時，說明重疊的 skill 與職責，建議改為優化它；使用者同意就改走優化，補齊優化需要的資訊並從 Phase 2 開始；仍要新建的，新 skill 的 description 在藍圖階段依選型規範寫明分界

## Good Example

- 列出已知與還缺的資訊，預期先擬一個樣子，並交代盤點結果

```text
已知：優化 release-notes，對話 92153031
還缺：預期（我先擬一個請你校正：「發版說明的最前面列出本版所有破壞性變更」）、你認為的原因
盤點：沒有與 release-notes 相關的未完成施工
```

## Bad Example

- 什麼資訊都沒列，使用者不知道該補什麼

```text
請問你要做什麼？
```

# Rule 12 - 預期寫成可判定的句子

- Level: `MUST`
- 每條預期編號為 E1、E2，是一句可以對照產出判定「有達成」或「沒達成」的話
- 預期寫結果，不寫手段，不寫「加一條規則」「用腳本」；使用者說的是手段時，換成他要的結果並請他校正，例如把「用腳本自動驗證」換成「不用人工比對就知道骨架與範例是否一致」
- 預期取自使用者的更正、不滿與說明，新建取自用途與預期產出；使用者說得模糊時，Phase 1 已先擬一個樣子請使用者校正，校正後的才是預期

## Good Example

- 兩條預期都能對照發版說明判定

```text
E1：發版說明的最前面列出本版所有破壞性變更
E2：發版說明的每一項變更都標註對應的 PR 編號
```

## Bad Example

- 第一條無法判定有沒有達成；第二條寫的是手段，不是結果

```text
E1：發版說明要更完整
E2：新增一條規則要求標示 PR 編號
```
