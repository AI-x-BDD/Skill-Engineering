# Rule 1 - 先判定問題型態，型態決定證據與預期的寫法

- Level: `MUST`
- 依使用者的說法判定問題型態，寫入診斷單的問題型態；兼有多型時以使用者最在意的一型為主，其餘寫在現況
- 單次失敗：某一次對話的結果不對；證據是該次對話的 trace，預期取自使用者在對話中的更正
- 重複性問題：使用者說「每次都」「又」；證據是兩份以上對話的 trace，比對共同的偏離點，使用者口述的「每次都」只是線索，不算證據；只有一份時先以這一份診斷，不中斷，並在尚缺證據請使用者補第二份；需要靠重複出現才能確認的根因（例如執行偏差），一份 trace 標推測、兩份以上標高度可能，讀檔就能看到的根因（SOP 沒有這一步、規範沒有這一條）仍可標已證實
- 結構性不滿：沒有失敗的對話，使用者覺得 skill 太雜、太長、難維護；證據是盤點的 step 數、規則數、衝突與重複，再以一個代表案例從頭走一遍，預期寫成可量測的結構目標；數字由使用者決定，使用者沒給時先擬草稿，在閘門 1 請使用者校正
- 能力擴充：使用者要 skill 多做一件事，或把現在靠人工做的事改成自動、可重現；證據是寫出一個用到新能力的具體案例，從第一個 step 走到最後一個 step，標出每個停住、衝突或沒有指示的地方，不只看與能力直接相關的規範，根因幾乎都是缺
- 效率成本：太慢或太耗 token；證據是 trace 的載入檔案時間線與 step 數，預期寫成可量測的上限
- 觸發問題：沒被觸發或跑到別的 skill；證據是 trace 中有沒有 Skill 呼叫、跑了誰
- 沒有對話紀錄的型態，診斷單案例欄的對話紀錄寫「無」，當時的輸入寫一句拿這個 skill 來做事的具體輸入（構造一個使用案例，由使用者在閘門 1 校正），不是使用者對 skill 的抱怨；現況寫用這個案例走查時停住、衝突或沒有指示的位置

## Good Example

- 使用者說「它每次都漏掉破壞性變更」，判為重複性問題，先確認有幾份對話紀錄

```text
問題型態：重複性問題
證據：v2.2 與 v2.3 兩份對話的 trace，比對共同的偏離點
```

## Bad Example

- 使用者說「想讓它也能產出英文版」，是能力擴充，卻當成單次失敗，在對話裡找不存在的錯

```text
問題型態：單次失敗
現況：產出的發版說明是中文版，與預期不符
```

# Rule 2 - 呼叫鏈由終點往回定位

- Level: `MUST`
- 先找出產出不滿意結果的 skill 作為終點，再逐段往上游判斷：這一段收到的輸入正確嗎？產出符合下一段的需要嗎？
- 第一個「輸入正確但產出不符」的段落是偏離點；輸入就已經錯，偏離點在更上游
- 呼叫鏈取自 trace 的 Skill 呼叫與 SOP 中 DELEGATE 的 skill，被委派的 skill 是委派者的上游，因為它的產出是委派者的輸入；沒有對話紀錄時，終點取使用者指定的目標 skill，上游取它 DELEGATE 的 skill
- 只有一個 skill 時，呼叫鏈只有一段

## Good Example

- 終點的輸入已不完整，繼續往上游找，偏離點落在 collect-changes

```text
release-notes 的輸出沒有破壞性變更段落
→ release-notes 收到的變更清單沒有破壞性變更欄位，輸入已不完整
→ collect-changes 收到的版本範圍正確，但產出缺欄位 → 偏離點在 collect-changes
```

## Bad Example

- 只因為使用者看到的是終點的輸出，就把偏離點定在終點，沒有檢查它收到的輸入

```text
偏離點：release-notes（使用者看到的發版說明是它產出的）
```

# Rule 3 - 走查只依 SOP 指定載入的檔案

- Level: `MUST`
- 走查是模擬當時的 AI：只能使用該 step 之前 SOP 已指定載入的檔案、description 與對話中已出現的內容
- 不因為自己讀過整個 skill，就補上當時的 AI 看不到的知識
- 走查範圍以產出有問題結果的 step 為中心：往前包含它依賴的 step 與載入的檔案，往後包含核對或接手這個結果的 step，直到該 skill 結束或把結果交給下一個 skill；結構性不滿與能力擴充走整份 SOP，並盤點全部部位檔，不受「只讀 SOP 指定載入的檔案」限制，但判斷到位時仍以各 step 之前 SOP 已指定載入的檔案為準
- 以 trace 的載入檔案時間線核對：SOP 有指定但 trace 沒讀，是執行偏差；SOP 沒有指定，是缺或漏載；腳本是執行不是讀取，腳本 step 不以載入時間線判定，trace 也看不到執行的指令與輸出，這類證據要請使用者提供輸出，或請使用者重跑
- 診斷單的走查範圍如實列出走查過的 step 範圍與載入的檔案，以及稽核回報的既有違規，並標明在走查範圍內或外

## Good Example

- SOP 沒有指定載入，trace 也沒讀，兩者一致，判為缺

```text
release-notes 的輸出 step 之前，SOP 沒有指定載入 rules/格式規範.md
trace：該檔沒有被讀取 → 與 SOP 一致，判為缺
```

## Bad Example

- 用自己讀過的規範內容替當時的 AI 補上知識，把問題誤判成執行偏差

```text
我讀過 rules/格式規範.md，裡面有要求標 PR 編號，所以 AI 應該知道 → 判為執行偏差
```

# Rule 4 - 用診斷階梯逐格判斷

- Level: `MUST`
- 由上而下逐格判斷，在第一個不成立的格記錄根因；下面的格仍可能同時有問題，也要各自判斷，診斷單的階梯欄可並列多格，以「；」分隔；沒有 trace 時，觸發與遵循兩格標「不適用」，其餘四格由走查判斷，交接看上游 SOP 交付的內容夠不夠下游用
- 觸發：description 能不能讓這個情境選到這個 skill，失敗型態是失觸發、入口競爭
- 交接：上游的產出有沒有送到下游，失敗型態是斷鏈
- 指示：SOP 有沒有 step 要求做這件事，失敗型態是缺
- 到位：做這件事時需要的規範、樣板與資訊，在這個 step 執行時已經載入了嗎，失敗型態是漏載、錯位、序錯
- 清晰：載入的內容讀得懂、彼此一致、沒有過載，失敗型態是糊、衝、贅、過載
- 遵循：前面五格都成立，AI 仍然做錯，失敗型態是執行偏差；這一格要最後才下結論，而且兩份以上 trace 重複出現同一個偏差時，根因改寫成缺少把關（指示：缺）：產出後沒有 step 核對這一項，或這一項可以交給腳本

## Good Example

- 逐格判斷，在指示格停下並記錄

```text
偏離點：collect-changes
觸發：成立（trace 有 Skill 呼叫）
交接：成立（收到的版本範圍正確）
指示：不成立（SOP 沒有讀取註腳的 step）→ 記錄：指示（缺）
```

## Bad Example

- 沒有檢查前面幾格，直接下「執行偏差」的結論

```text
AI 沒有標出破壞性變更 → 遵循（執行偏差）
```

# Rule 5 - 根因必須是 skill 檔案裡改得動的東西

- Level: `MUST`
- 根因寫到具體的檔案與位置，或寫出缺了什麼：description 的哪一句、SOP 的哪個 step、哪份規範的哪一條、哪份樣板、哪支腳本
- 「AI 不夠聰明」「使用者沒說清楚」「模型亂做」不是根因，繼續往下找；找不到時降為執行偏差的候選，證據等級標推測，兩份以上 trace 重複出現時可標高度可能

## Good Example

- 指到檔案與位置，也說出缺了什麼

```text
根因：RC1，collect-changes/SKILL.md 的 SOP 沒有任何 step 讀取 commit 的 BREAKING CHANGE 註腳
```

## Bad Example

- 把責任推給 AI，沒有任何 skill 檔案可以改

```text
根因：RC1，AI 沒有注意到 commit 的註腳
```

# Rule 6 - 每個落差至少考慮兩種成因

- Level: `MUST`
- 每個落差列出至少兩種可能的成因，逐一用證據排除或保留
- 診斷單的排除的可能，寫被排除的成因與排除它的證據
- 只有一種可能時，寫出為什麼沒有其他可能

## Good Example

- 兩種其他成因都附了排除的證據

```text
排除的可能：release-notes 看到欄位卻忽略（排除：清單裡沒有該欄位）；兩個 skill 沒被觸發（排除：trace 中兩個 Skill 呼叫都在）
```

## Bad Example

- 沒有考慮其他成因，也沒有說明為什麼

```text
排除的可能：無
```

# Rule 7 - 用反事實與證據等級檢驗根因

- Level: `MUST`
- 反事實：「若改掉這處，這次對話的結果會不同嗎？」答不出「會」，就不是根因
- 證據等級有三級：已證實（trace 或檔案內容直接看到）、高度可能（走查推得，缺 trace 驗證）、推測（只有推理）
- 每個根因都標一個證據等級，並在證據欄寫出支持它的 trace 或走查位置；產出內容有問題時，證據要引用產出物裡有問題的內容（trace 列出的寫入檔案，或使用者提供的檔案）
- 沒有對話的型態，反事實改問：改掉這處後，預期會達成嗎？不可退化清單會不會退化？

## Good Example

- 反事實答得出「會」，證據指到 trace 的內容，等級與證據相符

```text
證據：SOP 全文沒有讀取註腳的 step；trace 時間線中 collect-changes 沒有讀取任何含註腳的檔案
反事實：若 SOP 有 step 讀取註腳，變更清單就會帶破壞性變更的欄位，release-notes 就有內容可以排在最前面
證據等級：已證實
```

## Bad Example

- 反事實答不出「會」，卻標成已證實，也沒有寫證據

```text
反事實：即使加了這個 step，AI 也未必會用到
證據等級：已證實
```

# Rule 8 - 找不到根因就不進藍圖

- Level: `MUST`
- 有落差找不到任何根因，或所有根因的證據等級都是推測時，診斷單照常輸出，但在尚缺證據寫缺什麼與怎麼取得
- 閘門 1 的詢問改為請使用者補證據，不請使用者同意進入藍圖
- 常見的補證據方式：再一份對話紀錄、請使用者在新對話重跑目標 skill 並保留紀錄、請使用者補充說明；重跑由使用者在新對話進行，再回到本對話提供紀錄位置，本對話的診斷單繼續使用，不在本對話代為重跑，避免產生檔案或改動 skill
- 不用猜測推進到藍圖；只有已證實與高度可能的根因可以進藍圖，高度可能的相關列確度標中，使用者決定不補證據時照此處理；同一份診斷單混有推測的根因時，推測的不進藍圖，留在尚缺證據，也不要求有處置列；全是推測而使用者不補證據時，結案不施工，回報診斷單與尚缺證據
- 盤點後沒有落差（預期已達成，或要達成必須損失不可退化項）時，診斷單的現況寫明結論，請使用者決定結案或調整預期，不進藍圖

## Good Example

- 寫明缺什麼與怎麼取得

```md
## 尚缺證據

- 只有一份對話紀錄，無法區分是 RC2 還是偶發的執行偏差；請再提供一份同樣漏標 PR 編號的對話紀錄
```

## Bad Example

- 根因只是推測，卻直接進入藍圖

```text
根因：RC1，推測是 description 太長導致 AI 沒讀完
證據等級：推測
→ 請使用者同意診斷單，進入藍圖
```

# Rule 9 - 診斷單只談事實與因果，不談處方

- Level: `MUST`
- 診斷單不寫「應該改成」「建議新增」「可以刪除」，處置屬於藍圖
- 診斷單的每一句都能對到 trace、檔案內容或使用者的訊息

## Good Example

- 只說缺了什麼、為什麼是根因

```text
根因：RC1，collect-changes/SKILL.md 的 SOP 沒有任何 step 讀取 commit 的 BREAKING CHANGE 註腳
```

## Bad Example

- 診斷單裡直接開出處方，把診斷與藍圖混在一起

```text
根因：RC1，缺少讀取註腳的 step，應該在 Phase 1 新增一個 step 並新增一份規則
```

# Rule 10 - 列出不可退化清單

- Level: `MUST`
- 不可退化清單是目前做對、改完不能壞的結果，編號為 N1、N2，每項都能對照產出判定
- 來源有三種：預期中已經達成的部分；使用者沒有抱怨而且是 skill 賣點的產出特徵；現行 SOP 的關鍵行為
- 清單限於走查範圍內的結果，包含產出有問題結果之後的核對與接手 step 的結果；藍圖與驗收都以這份清單為準，它是敢刪的前提
- N# 以結果為單位，不是以規則條文為單位；不逐條反推現有規則，否則每個元素都能對到自己的 N#，預設刪除就失效；沒有對話時三種來源照用，現行 SOP 的關鍵行為由走查取得，並在閘門 1 請使用者補充要保留的行為

## Good Example

- 每項都能對照發版說明判定

```text
N1：變更依 feat、fix、chore 分組，目前的分組是正確的
N2：發版說明使用繁體中文，語氣維持現況
```

## Bad Example

- 沒有具體內容，無法判定有沒有退化

```text
N1：維持現有行為
```

# Rule 11 - 過去的施工紀錄只作線索

- Level: `SHOULD`
- 盤點結果列出目標 skill 過去的施工紀錄時，查看其診斷單與藍圖，確認與這次問題相關的規則或 step 當初為什麼存在，以及有沒有刪了又加的反覆
- 紀錄中的根因可能已過時，只當線索，結論以這次的證據為準
- 反覆出現的問題，在診斷單的現況註明

## Good Example

- 查了過去的藍圖，說明為什麼存在，並以這次的證據為準

```text
過去的施工紀錄：20260918-1010-release-notes 的藍圖第 4 列，因 E3 保留 rules/舊版格式.md；這次 E2 的格式要求與它衝突，以這次的證據為準
```

## Bad Example

- 直接採用過去診斷的根因，沒有用這次的證據驗證

```text
過去的診斷已經查出根因是 description，這次直接採用
```

# Rule 12 - 閘門 1 的詢問要列出使用者該檢視的事項

- Level: `MUST`
- 詢問時列出四件事：預期（E#）是否符合使用者的意思、每個根因是否同意、走查範圍有沒有漏掉的部位、不可退化清單是否完整；沒有對話紀錄的型態，案例是構造的，另請使用者確認它貼近實際會用的說法
- 使用者補了新的對話紀錄時，回到本 phase 取得對話紀錄的步驟重新取證；補充說明、不同意結論，或沒有對話紀錄的型態，回到分析落差與根因的步驟
- 使用者明確回覆同意才進入藍圖；回覆含修正時，改完診斷單再問一次，不視為同意

## Good Example

- 列出四件事，並說明補證據與不同意的處理

```text
請確認診斷單：
1. 預期 E1、E2 是否符合你的意思
2. 根因 RC1（collect-changes 沒有讀取註腳的 step）、RC2 是否同意
3. 走查範圍（collect-changes Phase 1、release-notes Phase 2）有沒有漏掉的部位
4. 不可退化清單 N1、N2 是否完整
補了新的對話紀錄我會重新取證；不同意結論我會重新分析
```

## Bad Example

- 只問一句「同意嗎？」，使用者不知道要看什麼，補證據與不同意也沒有分開處理

```text
診斷單如上，請問是否同意？
```
