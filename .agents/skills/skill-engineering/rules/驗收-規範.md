# Rule 1 - 盲測的任務書

- Level: `MUST`
- 由全新、沒有寫檔工具、也沒有本次對話內容的 agent（例如 Plan 類型），以案例走查改完的 skill
- 交付內容：目標 skill 的路徑（涉及多個 skill 時全部列出）、案例的輸入、行為預期（E# 全文）、不可退化清單（N# 全文，新建沒有）；結構性預期（條數、重複、長度）不交給盲測，由稽核的複雜度前後對照與語意完成條件判定
- 案例的輸入：取藍圖範例情境中的輸入句，不含期望的輸出；它已在閘門 2 經使用者確認，與診斷單的案例不同時以藍圖為準
- 不交付診斷單、藍圖、施工紀錄與本次對話的任何內容，避免 agent 看到答案
- 任務指示：你剛被這個輸入觸發，依 SOP 逐 step 走查，只能使用 SOP 已指定載入的檔案；每個 step 回報讀了什麼、會做什麼判斷或產出、遇到的缺口（資訊不足、規則衝突、指示含糊、沒有指示），每個缺口標明與哪一條預期有關，沒有關係的標「無關預期」；最後預測最終產出，逐條對照預期與不可退化清單，回報達成、未達成或無法判定
- 不實際執行腳本與委派，只描述會怎麼做；預期落在腳本輸出或被委派 skill 的產出時，只驗證指示與交付內容是否到位，其餘標為無法判定

## Good Example

- 只交付案例、預期與不可退化清單，並寫明走查的做法

```md
- 目標 skill：`.claude/skills/collect-changes`、`.claude/skills/release-notes`
- 案例輸入：幫我整理 v2.3 的發版說明
- 預期：E1 發版說明的最前面列出本版所有破壞性變更；E2 每一項變更都標註對應的 PR 編號
- 不可退化清單：N1 變更依 feat、fix、chore 分組；N2 使用繁體中文；N3 版本範圍由使用者指定的起訖 tag 決定；N4 腳本以退出碼 2 結束時，停下並回報原因，不用猜測補上內容
- 任務：你剛被上面的輸入觸發。依 SOP 逐 step 走查，只使用 SOP 已指定載入的檔案；每個 step 回報讀了什麼、會做什麼、遇到什麼缺口，每個缺口標明與哪一條預期有關，沒有關係的標「無關預期」；最後預測產出，逐條對照預期與不可退化清單，回報達成、未達成或無法判定。不要修改任何檔案，不要實際執行腳本。
```

## Bad Example

- 附上了診斷單，agent 看到根因就會替 skill 補上缺的知識，盲測失去意義

```md
- 目標 skill：`.claude/skills/collect-changes`
- 案例輸入：幫我整理 v2.3 的發版說明
- 診斷單：RC1 collect-changes 沒有讀取註腳的 step，請確認已修好
```

# Rule 2 - 落差分成實作偏差與設計落差

- Level: `MUST`
- 盲測回報的缺口、未達成與無法判定逐一歸類：與本次預期無關的缺口是既有缺口，不算落差，列入完工報告的未解決事項；未達成與跟預期有關的缺口算落差；無法判定的預期依下一條處理，不算落差
- 無法判定的預期，能補案例就補案例重測，補的案例輸入列入完工報告，補不了的列入完工報告的未解決事項，交由 L3 判定
- 實作偏差：藍圖的列沒有如實落實，SOP 或部位與藍圖不一致；退回該列補正，不重走閘門
- 設計落差：藍圖如實落實，預期仍未達成；優化時更新診斷單與藍圖並重新取得使用者同意，回到 Phase 2 分析落差與根因的步驟重新分析，不另加補丁；Phase 4 沿用同一個施工紀錄資料夾，baseline 保持第一輪施工前的原樣，診斷單與 blueprint.md 覆寫更新，blueprint.md 保留已完成的列
- 新建的設計落差：回到 Phase 3 的 THINK 步驟重做藍圖並重新取得同意；Phase 4 沿用同一個施工紀錄資料夾與已建的外殼；已建的部位視為這一輪藍圖的既有元素，沿用預設刪除、舉證保留：留下的，原本新增的列維持新增與已完成，不要的，把那一列改成刪除並重新待辦，依編排規範刪除本次施工建立的檔案；複雜度的「前」取第一輪施工後的結果（稽核對新建只算得到 0，改以第一輪藍圖複雜度表的「後」填寫，RUN-GROWTH 警告不計），blueprint.md 覆寫並保留留下的已完成列
- 補正後重新稽核並重新盲測，直到沒有落差；同一項補正兩次仍未解決，停止並回報使用者

## Good Example

- 一個是實作偏差、一個是設計落差，處理方式不同

```text
缺口：release-notes Phase 2 沒有載入格式規範 → 藍圖第 3 列已列為改寫，但 SOP 沒有該 step → 實作偏差，退回第 3 列補正
未達成：E1，SOP 與規範都如實落實，盲測仍沒有把破壞性變更排在最前面 → 設計落差，回到 THINK 重新分析
```

## Bad Example

- 設計落差直接加一條規則補丁，沒有回頭分析根因

```text
未達成：E1，盲測仍沒有把破壞性變更排在最前面 → 在格式規範新增一條「破壞性變更要排最前面」
```

# Rule 3 - 驗收等級

- Level: `MUST`
- L1：稽核腳本的結構檢查與藍圖追溯沒有新增的違規；施工前就有的既有違規（稽核另列為 pre_existing）不阻擋 L1，列在完工報告的未解決事項
- L2：L1 通過，且盲測走查沒有落差，也就是每條行為預期都是達成、結構性預期由稽核判定達成；既有缺口不影響 L2，有無法判定的預期只能到 L1
- L3：L2 通過，且使用者在新對話以原案例實跑通過
- 本流程最多達到 L2，L3 只有使用者能達成；完工報告寫「未實跑」，並附一句可直接貼上的重跑輸入，也就是盲測用的案例輸入，不是最初的建立請求，也不是對 skill 的抱怨
- L1、L2 都不含腳本實跑，腳本的驗收案例結果併入完工報告：新增的腳本由 /skill-derive-script 實跑並回報，改寫的腳本由 skill-engineering 在該列核對時實跑
- 驗收等級依實際做到的寫，沒做的驗收寫「未做」，不寫「已驗證」

## Good Example

- 如實標明等級，L3 附上重跑輸入

```text
驗收等級：L2（稽核 0 違規；盲測無落差）
L3：未實跑。請在新對話輸入「幫我整理 v2.3 的發版說明」重跑
```

## Bad Example

- 沒有等級，也把沒做過的實跑寫成已驗證

```text
驗收：已驗證通過
```

# Rule 4 - 腳本無法判定的語意完成條件

- Level: `MUST`
- 藍圖每一列的內容確實落實：對照實際檔案，不只看狀態欄
- 每個處置確實對準診斷單的根因，不是形式上引用編號
- 淨複雜度增加的部分，都能指到根因
- 診斷單的不可退化清單每一項，在改完的 skill 中仍有對應的 step 或規則
- 新建沒有診斷單與不可退化清單，改核：每個新增列都對應一個預期（E#）、沒有對不到預期的部位、範例情境能由 SOP 走通；盤點顯示職責重疊的，新 skill 的 description 寫明與重疊 skill 的分界
- 改過 description 時，原有的觸發情境仍被涵蓋，或刪除的理由已寫在藍圖
- 目標是 derive 或 form skill，或是 skill-engineering 自己時，依改完後的規範重新檢查它的 SOP，兩者一致
- 有落差依編排規範的落差補正責任處理，補正後回到本 phase 的稽核步驟重跑

## Good Example

- 打開實際檔案核對藍圖第 5 列

```text
藍圖第 5 列：collect-changes/rules/破壞性變更-規範.md 定義哪些 commit 算破壞性變更
核對：打開該檔，Rule 1 定義 `!` 標記，Rule 2 定義 `BREAKING CHANGE` 註腳 → 落實
```

## Bad Example

- 只看狀態欄全是已完成，就當成完成

```text
blueprint.md 的狀態欄全是已完成或無需施工 → 語意核對通過
```

# Rule 5 - 完工報告

- Level: `MUST`
- 欄位有變更清單（每列的位置、處置、一句話原因）、刪除清單（含刪除的原因，沒有則寫「無」）、複雜度前後、驗收等級（含盲測的摘要、腳本驗收案例的結果，沒有腳本則寫「無」，與 L3 的重跑輸入）、施工紀錄的位置、未解決事項（含既有缺口、無法判定的預期、藍圖「受影響的 skill」欄寫下的建議；沒有則寫「無」）
- 在對話中回報，同時存為施工紀錄資料夾的 `report.md`
- 只寫可對照的事實，不寫「應該沒問題」「看起來正常」這類無法對照的語句

## Good Example

- 欄位齊全，內容可對照

```md
# 完工報告 - release-notes

## 變更清單

- collect-changes/SKILL.md#Phase 1：改寫，取得 commit 的 step 改為取得標題與註腳（RC1）
- collect-changes/scripts/list_commits.py：改寫，輸出加入註腳（RC1）
- collect-changes/SKILL.md#Phase 2：改寫，分組輸出的 step 加上標出破壞性變更（RC1）
- collect-changes/rules/破壞性變更-規範.md：新增，定義哪些 commit 算破壞性變更（RC1）
- release-notes/SKILL.md#Phase 2：改寫，輸出前加入讀取格式規範的 step（RC2）

## 刪除清單

- release-notes/rules/舊版格式.md：已被格式規範取代，沒有任何 step 載入

## 複雜度前後

- step 數 8 → 10；規則數 8 → 9；總行數 323 → 348

## 驗收

- L2：稽核 0 違規；盲測無落差
- 腳本驗收案例：`list_commits.py` 正例退出碼 0、反例退出碼 2（改寫的腳本，由 skill-engineering 在該列核對時實跑）
- L3：未實跑，請在新對話輸入「幫我整理 v2.3 的發版說明」重跑

## 施工紀錄

- `.claude/engineering-runs/20261025-1430-release-notes/`

## 未解決事項

- 無
```

## Bad Example

- 沒有欄位，也沒有可對照的內容

```md
改好了，應該沒問題。
```
