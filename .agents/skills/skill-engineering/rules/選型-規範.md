# Rule 1 - 先為預期從零設計主幹

- Level: `MUST`
- 優化也先為預期（E#）與不可退化清單（N#）設計理想的主幹，也就是 Phase 與 step 的序列；設計時不以現有 SOP 的形狀為前提，即使已經走查過
- 根因在部位內文時，主幹照現行即可，從零設計改為為預期設計理想的規則集：要有哪些規則、各管什麼
- 再把現有元素逐一對照這份理想設計，決定保留、改寫、刪除或新增；不在預期與不可退化清單裡的元素，是刪除候選
- 新建本來就是從零設計
- 預期旁寫一個範例情境，它同時是驗收與使用者重跑的案例輸入：輸入句優化時沿用診斷單案例的當時輸入（多組時取第一組或使用者最在意的一組，沒有對話的優化沿用構造的案例），新建取使用者說明的使用輸入，沒說明時依用途構造一句；當時的輸入不能獨立使用時（多輪脈絡中的短句、委派交付單），改寫成一句獨立可用的輸入；構造與改寫的都在閘門 2 請使用者確認

## Good Example

- 先依預期設計，再對照現有 SOP 決定處置

```text
預期：E1 破壞性變更排最前面、E2 每項標 PR 編號
範例情境：輸入「幫我整理 v2.3 的發版說明」（診斷單案例的當時輸入）
理想主幹（不看現有 SOP）：Phase 1 讀取變更 → Phase 2 輸出發版說明
現有 SOP：Phase 1 讀取變更、Phase 2 分類、Phase 3 排序、Phase 4 輸出
對照後：Phase 2 與 Phase 3 合併為一個 step，其餘保留
```

## Bad Example

- 直接在現有 SOP 上加一個 step，沒有重新設計

```text
在現有 SOP 的 Phase 4 前面加一個 step「檢查有沒有破壞性變更」
```

# Rule 2 - 主幹先於部位

- Level: `MUST`
- 先決定 Phase 與 step，只用 SOP 的五個動詞（READ、WRITE、THINK、DELEGATE、ASK）；再決定哪些 step 要展開成規則、樣板或腳本
- 部位是 step 的展開，不是流程本身；主幹沒有的流程，不能靠部位偷渡

## Good Example

- 流程在主幹，規則只把關判斷的標準

```text
主幹：THINK 依破壞性變更規範判定每個 commit 是否為破壞性變更
部位：rules/破壞性變更-規範.md 只定義哪些 commit 算破壞性變更
```

## Bad Example

- 把流程寫進規則檔，SOP 看不到這些 step

```text
rules/破壞性變更-規範.md
# Rule 1 - 先讀註腳
# Rule 2 - 再依類型分組
# Rule 3 - 最後排序輸出
```

# Rule 3 - Phase 與 step 的切分

- Level: `SHOULD`
- 每個需要使用者確認的點，與每個結果型產出，各切出一個 Phase 邊界；Phase 標題以動詞開頭，產出結果的 Phase 寫成「完成○○」
- 一個 Phase 通常 3 到 8 個 step；後一個 Phase 必須用到前一個 Phase 的產出
- 一個 step 要求太多事就拆開；沒有獨立產出的 step 不拆，也不單獨成立

## Good Example

- 確認點切出 Phase 邊界，標題是結果

```text
Phase 1 -- 讀取版本範圍內的 commit
Phase 2 -- 完成變更清單並取得確認
Phase 3 -- 完成發版說明
```

## Bad Example

- 為了分類切出沒有產出的 Phase，標題是抽象詞

```text
Phase 1 -- 準備
Phase 2 -- 其他
```

# Rule 4 - 部位選型：腳本、樣板、規則，或留在 SOP

- Level: `MUST`
- 輸入輸出確定、結果可判定對錯，而且 AI 做會偏差或每次都要重做：選腳本
- 約束的是產出檔案的結構與格式：選樣板
- 約束的是判斷或品質，條列式寫得完：選規則；只有一個 step 用到的做 step 級，多個 step 或兩種模式都用到的做全域，在第一個用到的 step 前載入
- 一句話講得完的：留在 SOP 的 step，不另立部位
- 判不準時選較輕的，由輕到重依序是 SOP、規則、樣板、腳本，部位日後可以再展開

## Good Example

- 每個 step 依特性選型

```text
讀取 commit 的標題與註腳：輸入輸出確定，結果可判定 → 腳本
判定哪些 commit 算破壞性變更：需要判斷，條列式寫得完 → 規則
發版說明的段落結構：產出檔案的格式 → 樣板
確認版本範圍的起訖 tag：一句話講得完 → 留在 step
```

## Bad Example

- 判定破壞性變更需要理解 commit 的內容，不是確定性的工作，卻選了腳本

```text
判定哪些 commit 算破壞性變更 → 腳本
```

# Rule 5 - 預設刪除，舉證保留

- Level: `MUST`
- 處置範圍內的每個既有元素預設刪除；元素的粒度是 SOP 的一個 step、規則檔內的一條 Rule、一份樣板、一支腳本、description 的一句話、整份規則檔
- 要保留必須在依據欄寫出它對應的預期（E#）或不可退化項（N#）；閘門 2 使用者要求保留的元素，依據寫「使用者指定」
- 找不到對應的元素一律刪除，依據寫「無舉證」；刪除在任何粒度都寫刪除，執行時委派 /skill-form-*，整份檔案才由 skill-engineering 刪
- 刪除列的位置：整份檔案寫檔案路徑；檔內單條寫到該條，用規則標題不用編號（`<檔案>#<規則標題>`），因為前面的列施工後編號會位移；SOP 的 step 也單獨一列，位置寫到所在的 Phase，內容引該 step 的原文
- 多個元素對到同一個 N# 而且內容重複時，保留最能表達它的一個，其餘依據寫「無舉證」刪除；功能不同的不算重複，例如一個約束產出、一個核對產出；合併寫成吸收的元素處置改寫、被吸收的元素處置刪除，兩列的內容互相指明，跨檔搬規則時改寫列的交付單附要搬入的規則原文
- 處置表逐被處置的元素列出，保留的元素可按同一個依據合併成一列，位置寫到 Phase 或整份檔案；處置範圍內主幹標「（不變）」的 Phase 也要在處置表有一列保留；SOP 內同一個 Phase 的改寫與新增 step 可合併成一列，處置寫改寫，內容逐 step 說明，只新增 step 的 Phase 寫新增，刪除的 step 不合併
- 刪除不是風險，優化時有 baseline 可以還原

## Good Example

- 沒有任何 step 載入、也對不到預期的規則檔，直接刪除

```md
| 8 | release-notes/rules/舊版格式.md | 已被格式規範取代，沒有任何 step 載入 | 刪除 | 無舉證 | 高 | 待辦 |
```

## Bad Example

- 保留以防萬一，依據卻寫「無舉證」，違反舉證保留

```md
| 8 | release-notes/rules/舊版格式.md | 暫時用不到，保留以防萬一 | 保留 | 無舉證 | 低 | 無需施工 |
```

# Rule 6 - 有因必處，無因不改

- Level: `MUST`
- 診斷單的每個根因（RC#）至少對應一列改寫、刪除或新增的處置；證據等級為推測的根因除外，它不進藍圖（根因分析規範），留在診斷單的尚缺證據
- 有舉證保留、但沒有根因指向的元素，維持原樣，狀態寫無需施工
- 新增必須有根因；沒有根因的新增是疊床架屋，不得出現
- 新建沒有診斷單，以預期（E#）代替根因（RC#）：每個預期至少對應一列新增，新增的依據寫 E#；沒有對應預期的部位不建
- 新建的處置表：第一列是 `<skill 名稱>/SKILL.md#description`，SKILL.md 以 Phase 為粒度各一列，每個部位檔一列（委派對象必然附帶的檔案，例如第一支腳本附上的腳本執行規範，不另列，算進複雜度），處置都寫新增，狀態初始為待辦
- 優化的處置表在閘門 2 的初始狀態：改寫、刪除、新增的列寫待辦，保留的列寫無需施工；已完成是施工核對後才改

## Good Example

- 新增的規則檔依據是 RC1

```md
| 5 | collect-changes/rules/破壞性變更-規範.md | 定義哪些 commit 算破壞性變更與標記方式 | 新增 | RC1 | 中 | 待辦 |
```

## Bad Example

- 優化時，新增樣板只是為了讓格式更一致，依據沒有指到任何根因

```md
| 10 | release-notes/templates/release-notes.md | 新增發版說明樣板，讓格式更一致 | 新增 | E1 | 低 | 待辦 |
```

# Rule 7 - 處方層級不低於根因層級

- Level: `MUST`
- 層級由高到低是 description、SOP 主幹、step 的展開（規則、樣板、腳本的存廢）、部位的內文
- 根因在哪一層，處置就在那一層或更高：根因在 description 就改 description；缺 step 就補 step；不用加規則去提醒 AI 做主幹沒要求的事
- 不能用較低層級的處置掩蓋較高層級的根因

## Good Example

- 根因在 description，處置也在 description

```text
RC3：description 沒有寫「整理發版說明」的說法（description 層）
處置：release-notes/SKILL.md#description 改寫，補上觸發說法
```

## Bad Example

- 根因在 description，卻在 SOP 補一個 step 去確認，使用者的說法照樣不會觸發這個 skill

```text
RC3：description 沒有寫「整理發版說明」的說法（description 層）
處置：在 SOP 加一個 step「確認使用者要的是發版說明」
```

# Rule 8 - 淨複雜度預算

- Level: `MUST`
- 藍圖的複雜度表列出前後的 Phase 數、step 數、規則數、樣板數、腳本數與總行數；「後」以施工完成後的狀態估計，新增部位的載入 step 與必然附帶的檔案（例如第一支腳本會附上腳本執行規範）也要算進去
- 預設後不大於前；增加的項目，在後欄數字後以括號，或在對應列的內容，寫出多出的部分對應哪個根因
- 無法對應根因的增加，刪掉
- 新建的「前」全為 0，預算改看每個新增的部位是否對應預期

## Good Example

- step 數增加 1，在對應列說明是為了 RC1

```md
| step 數 | 7 | 8 |
```

```md
| 2 | collect-changes/SKILL.md#Phase 2 | 新增判定破壞性變更的 step（step 數 +1，對應 RC1） | 新增 | RC1 | 高 | 待辦 |
```

## Bad Example

- 規則數從 5 增加到 8，沒有任何一列說明多出來的規則對應哪個根因

```md
| 規則數 | 5 | 8 |
```

# Rule 9 - 處置不得破壞不可退化清單

- Level: `MUST`
- 每列處置都對照診斷單的不可退化清單（N#）；處置可能影響清單項目時，該列確度標低，並在內容寫出影響，交使用者在閘門 2 決定
- 新建沒有清單，以預期與範例情境代之

## Good Example

- 合併分類與排序可能影響 N1，確度標低並寫出影響

```md
| 3 | release-notes/SKILL.md#Phase 1 | 合併分類與排序，可能影響 N1 的分組順序 | 改寫 | RC2、N1 | 低 | 待辦 |
```

## Bad Example

- 合併分類與排序會影響 N1 的分組，卻標成高確度，沒有提到影響

```md
| 3 | release-notes/SKILL.md#Phase 1 | 合併分類與排序 | 改寫 | RC2 | 高 | 待辦 |
```

# Rule 10 - 處置範圍預設為走查範圍

- Level: `MUST`
- 只處置診斷單走查範圍內的元素；範圍外的元素不列處置列
- description 與 frontmatter 預設不在處置範圍；診斷階梯的觸發格不成立，或預期要改變觸發說法時才納入，納入時依 description 規定
- 根因在主幹的形狀（整個流程錯位），或範圍內到處是贅與衝時，提議擴大到整個 skill，在處置範圍的擴大理由寫出原因，由使用者在閘門 2 決定
- 目標 skill 被其他 skill 委派時（盤點的呼叫關係），在藍圖寫出受影響的 skill 與影響；它們不列處置列
- 走查範圍內只是呼叫鏈經過、預期與根因都不在其中的 skill 或檔案，在處置範圍的僅走查欄寫出名稱與理由，不進處置範圍：不列處置列，也不做預設刪除；使用者可在閘門 2 要求納入

## Good Example

- 呼叫鏈經過的 collect-changes 預期與根因都不在其中，標為僅走查

```md
- 範圍：走查範圍
- 擴大理由：無
- 僅走查：collect-changes，只是呼叫鏈經過，預期與根因都不在其中
```

## Bad Example

- 範圍是走查範圍，卻順手處置了範圍外的規則檔，沒有經過使用者決定

```md
- 範圍：走查範圍
- 擴大理由：無

| 7 | release-notes/rules/語氣-規範.md | 順手精簡 | 改寫 | 無舉證 | 低 | 待辦 |
```

# Rule 11 - 每列標依據與確度

- Level: `SHOULD`
- 依據寫 RC#、E#、N#、「使用者指定」或「無舉證」，可同時寫多個；使用者指定只能搭配保留，無舉證只能搭配刪除
- 確度：高是根因已證實且處置直接，中是根因高度可能或處置的內文需要使用者校正，低是處置影響不可退化項（根因為推測的不進藍圖）；新建沒有根因，高是預期明確且做法直接，中是做法需要使用者校正，低是預期本身仍模糊

## Good Example

- 新建以預期為依據，確度中表示做法需要使用者校正

```md
| 2 | collect-changes/rules/破壞性變更-規範.md | 定義哪些 commit 算破壞性變更與標記方式 | 新增 | E2 | 中 | 待辦 |
```

## Bad Example

- 依據欄空白，確度也沒有依據可判斷

```md
| 2 | collect-changes/rules/破壞性變更-規範.md | 定義哪些 commit 算破壞性變更與標記方式 | 新增 |  | 高 | 待辦 |
```

# Rule 12 - description 寫觸發情境與分界

- Level: `SHOULD`
- 內容依序是何時用（觸發情境與使用者常見的說法）、做什麼、相鄰 skill 的分界；沒有相鄰 skill 時不寫分界句
- 新建時盤點顯示職責重疊而使用者仍要新建的，新 skill 的 description 寫明「X 請改用 Y」的分界；現有 skill 的 description 不在這次施工改動，補分界句的建議寫在藍圖的受影響的 skill，並列入完工報告的未解決事項
- 不寫 SOP 的步驟與細節
- 新建時，藍圖處置表要有 `<skill 名稱>/SKILL.md#description` 一列，內容欄寫出 description 全文草稿，閘門 2 由使用者校正，Phase 4 以它建立外殼
- 改寫既有的 description 時，原有的觸發情境逐項保留，或在藍圖列寫出刪除的理由

## Good Example

- 觸發說法、做什麼、分界都有

```text
當要整理某個版本的發版說明或 changelog 時使用，例如「整理 v2.3 的發版說明」「幫我寫 changelog」。產出依破壞性變更、功能、修正分段的發版說明。只要列出 commit 清單請改用 collect-changes。
```

## Bad Example

- 寫的是 SOP 細節，沒有觸發情境，也沒有分界

```text
這個 skill 有三個 Phase：先收集 commit，再分組，最後輸出發版說明
```

# Rule 13 - 閘門 2 的詢問要列出使用者該檢視的事項

- Level: `MUST`
- 詢問時單獨列出：處置為刪除的列、確度低的列、範例情境（尤其是 AI 構造的）、處置範圍（含僅走查）與擴大理由、交付單中由草稿填的欄位（例如驗收案例、第三方套件、腳本與 AI 的分工）；新建時另列 description 草稿
- 使用者要求調整處置時，回到本 phase 的 THINK 步驟；調整會推翻預期或根因時，優化回到 Phase 2 分析落差與根因的步驟，新建回到 Phase 1 的詢問
- 使用者明確回覆同意才進入 Phase 4；回覆含修正時，改完藍圖再問一次，不視為同意

## Good Example

- 單獨列出刪除、低確度與 AI 構造的範例情境

```text
請特別檢視：
刪除：第 8 列 release-notes/rules/舊版格式.md（無舉證）
確度低：第 3 列 release-notes/SKILL.md#Phase 1（可能影響 N1）
範例情境：輸入「幫我整理 v2.3 的發版說明」（我構造的，請確認是你會用的說法）
處置範圍：走查範圍，沒有擴大，沒有僅走查的項目
交付單草稿：collect-changes/scripts/list_commits.py 的驗收案例與腳本和 AI 的分工是我擬的，請確認
```

## Bad Example

- 只問「藍圖有 5 列，同意嗎？」，沒有挑出任何需要檢視的事項

```text
藍圖共 5 列，請問是否同意？
```
