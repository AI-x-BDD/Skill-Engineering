# Rule 1 - 不得有互動式輸入

- Level: `MUST`
- 腳本不可使用 `input()`、`getpass` 或任何等待使用者輸入的互動流程，因為 AI 在非互動的 shell 中執行，會一直卡住
- 所有輸入都來自命令列參數、環境變數或 stdin
- 缺少必要參數時，立即輸出錯誤與用法，並以退出碼 2 結束

## Good Example

- 輸入來自命令列參數；缺少 `rulefile` 時 argparse 會輸出用法並以 2 結束

```python
parser = argparse.ArgumentParser(description=__doc__)
parser.add_argument("rulefile", help="要檢查的 RuleFile 路徑")
args = parser.parse_args()
```

## Bad Example

- 等待使用者輸入，AI 無法回應，腳本會一直卡住

```python
rulefile = input("請輸入要檢查的 RuleFile 路徑：")
```

# Rule 2 - 退出碼固定三種

- Level: `MUST`
- `0`：成功，沒有發現問題
- `1`：腳本正常跑完，但發現問題；問題清單寫在 stdout
- `2`：腳本無法執行，例如參數錯誤、輸入檔不存在、缺少相依套件；原因與處理方式寫在 stderr
- 退出碼的意義寫進腳本開頭的 docstring，讓 `--help` 顯示出來
- 未預期的例外要攔住，以 2 結束並在 stderr 說明；Python 對未攔住的例外是以 1 結束，會被誤認成「發現問題」

## Good Example

- 三種結果各用一個退出碼：`main()` 回傳 0 或 1，已知的無法執行情況回傳 2，未預期的例外也歸到 2

```python
def main() -> int:
    ...
    if not path.is_file():
        print(f"[無法執行] 找不到檔案 {path.as_posix()}", file=sys.stderr)
        return 2
    ...
    return 1 if problems else 0


if __name__ == "__main__":
    try:
        sys.exit(main())
    except Exception as e:
        print(f"[無法執行] {type(e).__name__}: {e}", file=sys.stderr)
        sys.exit(2)
```

## Bad Example

- 用 1 表示「無法執行」，與「發現問題」無法區分，AI 會誤以為要修改產出

```python
if not path.exists():
    sys.exit(1)
```

# Rule 3 - 使用 argparse 並提供 `--help`

- Level: `MUST`
- 命令列介面一律使用標準庫 `argparse`
- 腳本開頭的 docstring 寫明用途、用法範例與退出碼，並交給 `argparse` 當說明，讓 `--help` 完整顯示
- `--help` 的內容保持精簡，它的輸出會進入 AI 的上下文

## Good Example

- docstring 寫明用途、用法與退出碼，`--help` 直接顯示

```python
"""檢查 RuleFile 的 Rule 編號是否連續。

用法：
    uv run check_rulefile.py <RuleFile 路徑>

退出碼：
    0  通過
    1  有違規（清單以 JSON 寫在 stdout）
    2  無法執行（原因寫在 stderr）
"""
import argparse

parser = argparse.ArgumentParser(
    description=__doc__,
    formatter_class=argparse.RawDescriptionHelpFormatter,
)
parser.add_argument("rulefile", help="要檢查的 RuleFile 路徑")
```

## Bad Example

- 自己解析 `sys.argv`，沒有 `--help`，AI 無從得知腳本需要什麼參數

```python
import sys

path = sys.argv[1]
```

# Rule 4 - 結果寫 stdout，診斷寫 stderr，輸出大小要可預期

- Level: `MUST`
- 腳本的結果寫到 stdout，預設使用 JSON 或單行摘要，讓 AI 與其他工具都能解析
- 進度、警告與錯誤原因寫到 stderr，不混進 stdout
- 輸出可能很大時，預設只輸出摘要或設定上限，完整內容用 `--output <檔案>` 寫成檔案並回傳路徑；AI 的執行環境常會截斷過長的輸出

## Good Example

- 結果是 stdout 上的一行 JSON，進度寫到 stderr

```python
print(json.dumps({"violations": violations}, ensure_ascii=False))
print(f"已檢查 {count} 條規則", file=sys.stderr)
```

## Bad Example

- 進度與結果混在 stdout，AI 無法解析哪些是結果

```python
print("開始檢查…")
print("Rule 3 缺少 Level 欄位")
print("完成")
```

# Rule 5 - 錯誤訊息要說明原因、期望與下一步

- Level: `MUST`
- 錯誤訊息要寫出發生了什麼、期望的是什麼、下一步該怎麼做
- 檢查類腳本回報的問題，要指出具體位置（檔案、行號或項目名稱）與修正方向，讓 AI 不用再猜

## Good Example

- 檢查結果指出位置、問題與修正方向

```json
{"violations": [{"file": "rules/實作-格式規範.md", "rule": "Rule 3", "problem": "缺少 Level 欄位", "fix": "在標題下一行補上 Level 欄位，值為 MUST、SHOULD 或 MAY"}]}
```

- 參數錯誤時說明收到什麼、可接受什麼，並附上用法

```text
[無法執行] --format 只接受 json、csv、table，收到 "xml"。
用法：uv run export_report.py --format json data.csv
```

## Bad Example

- 只說有錯，沒有位置、期望與方向

```text
Error: invalid input
```

# Rule 6 - 腳本可重跑，寫入有保護

- Level: `SHOULD`
- 腳本重複執行同樣的輸入，結果要相同；「不存在才建立」優於「建立，已存在就失敗」
- 會寫入或刪除檔案的腳本，預設不覆寫既有檔案，要覆寫必須明確傳入 `--force`
- 會寫入或刪除檔案的腳本提供 `--dry-run`，只列出會做的事，不實際執行

## Good Example

- 預設不覆寫，提供 `--force` 與 `--dry-run`

```python
parser.add_argument("--force", action="store_true", help="覆寫已存在的輸出檔")
parser.add_argument("--dry-run", action="store_true", help="只列出會寫入的檔案，不實際寫入")
```

## Bad Example

- 不檢查就覆寫既有檔案，重跑一次就蓋掉先前的結果

```python
Path(args.output).write_text(content, encoding="utf-8")
```
