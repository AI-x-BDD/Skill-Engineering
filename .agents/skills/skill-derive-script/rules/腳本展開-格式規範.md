# Rule 1 - 展開單位

- Level: `MUST`
- 每次展開只處理使用者指定的一個 step
- 每個被展開的 step 對應一支腳本；多個 step 需要相同的邏輯時，後面的 step 沿用既有腳本，不重複建立

## Good Example

- 使用者指定 Phase 2 第 3 步，只為它建立一支腳本

```text
scripts/
└── check_error_codes.py
```

## Bad Example

- 使用者只指定一個 step，卻順便替其他 step 也建立腳本

```text
scripts/
├── check_error_codes.py
├── list_endpoints.py
└── format_changelog.py
```

# Rule 2 - 腳本只取代可確定性完成的部分

- Level: `MUST`
- 腳本只承擔能用程式確定性完成的工作，例如解析、檢查、轉換、產生檔案
- 需要判斷、取捨或創作的部分，留在腳本之後的 `THINK` 或 `WRITE` step，由 AI 處理
- 向使用者提問留在 `ASK` step，不交給腳本
- 原 step 同時含確定性與判斷兩部分時，拆成「`DELEGATE` 腳本」與「後續 step」兩個 step

## Good Example

- Before：一個 step 同時包含檢查與補正

```md
3. READ 逐條對照錯誤碼文件，確認每個錯誤碼都有 HTTP 狀態與重試建議，缺漏的立即補正。
```

- After：檢查交給腳本，補正留給 AI

```md
3. READ 讀取 `rules/腳本執行-格式規範.md`，將其視為唯一腳本執行規範來源。
4. DELEGATE 依腳本執行規範執行 `scripts/check_error_codes.py`，傳入錯誤碼文件路徑，取回缺漏清單。
5. WRITE 依缺漏清單補正錯誤碼文件。
```

## Bad Example

- 把補正也交給腳本；補寫重試建議需要理解 API 的行為，不是確定性的工作

```md
4. DELEGATE 依腳本執行規範執行 `scripts/check_error_codes.py`，傳入錯誤碼文件路徑，由腳本檢查並補齊缺漏的重試建議。
```

# Rule 3 - 插入載入 step

- Level: `MUST`
- 在整份 SOP 中第一個腳本 step 的正前方，插入一個 `READ` step，載入目標 skill 的腳本執行規範
- 該 `READ` step 寫出完整路徑 `rules/腳本執行-格式規範.md`，並寫明「將其視為唯一腳本執行規範來源」
- 之後的腳本 step 以「依腳本執行規範」指明依據，不再寫路徑，也不再插入 `READ`
- 新腳本 step 若比既有的載入 step 更早出現在 SOP 中，把載入 step 搬到新腳本 step 的正前方，原位置刪除
- 同一 phase 中位於其後的 step 編號依序遞增

## Good Example

- Before

```md
## Phase 2 -- 完成錯誤碼文件

1. THINK 依需求整理本次要新增的錯誤碼。
2. WRITE 撰寫錯誤碼文件。
3. READ 逐條對照錯誤碼文件，確認每個錯誤碼都有 HTTP 狀態與重試建議。
```

- After：在第 3 步前插入載入 step，原第 3 步變成第 4 步

```md
## Phase 2 -- 完成錯誤碼文件

1. THINK 依需求整理本次要新增的錯誤碼。
2. WRITE 撰寫錯誤碼文件。
3. READ 讀取 `rules/腳本執行-格式規範.md`，將其視為唯一腳本執行規範來源。
4. DELEGATE 依腳本執行規範執行 `scripts/check_error_codes.py`，傳入錯誤碼文件路徑，取回缺漏清單。
```

- 另一種情況：載入 step 原本在 Phase 3，新腳本 step 在更早的 Phase 2，載入 step 搬到 Phase 2，Phase 3 的腳本 step 改以名稱稱呼

```md
## Phase 2 -- 完成錯誤碼文件

1. THINK 依需求整理本次要新增的錯誤碼。
2. WRITE 撰寫錯誤碼文件。
3. READ 讀取 `rules/腳本執行-格式規範.md`，將其視為唯一腳本執行規範來源。
4. DELEGATE 依腳本執行規範執行 `scripts/check_error_codes.py`，傳入錯誤碼文件路徑，取回缺漏清單。

## Phase 3 -- 完成端點清單

1. DELEGATE 依腳本執行規範執行 `scripts/list_endpoints.py`，傳入原始碼目錄，取回端點清單。
```

## Bad Example

- 載入 step 放到 Phase 1，失去按需載入的效果

```md
## Phase 1 -- 讀取需求

1. READ 讀取 `rules/腳本執行-格式規範.md`，將其視為唯一腳本執行規範來源。
```

- 每個腳本 step 前都重複插入載入 step

```md
3. READ 讀取 `rules/腳本執行-格式規範.md`，將其視為唯一腳本執行規範來源。
4. DELEGATE 依腳本執行規範執行 `scripts/check_error_codes.py`，傳入錯誤碼文件路徑，取回缺漏清單。
5. READ 讀取 `rules/腳本執行-格式規範.md`，將其視為唯一腳本執行規範來源。
6. DELEGATE 依腳本執行規範執行 `scripts/list_endpoints.py`，傳入原始碼目錄，取回端點清單。
```

# Rule 4 - 改寫被展開的 step

- Level: `MUST`
- 被展開的 step 改寫為 `DELEGATE`，寫明腳本路徑、傳入內容與取回內容
- 腳本路徑相對於 skill 目錄，例如 `scripts/check_error_codes.py`
- 不寫 `uv run`、命令列旗標與參數名稱，也不重述腳本內部的邏輯；執行方式由腳本執行規範負責，用法由腳本的 `--help` 說明

## Good Example

- Before

```md
3. READ 逐條對照錯誤碼文件，確認每個錯誤碼都有 HTTP 狀態與重試建議。
```

- After：動詞改為 `DELEGATE`，寫明腳本、傳入與取回

```md
4. DELEGATE 依腳本執行規範執行 `scripts/check_error_codes.py`，傳入錯誤碼文件路徑，取回缺漏清單。
```

## Bad Example

- 寫出了 `uv run`、命令列旗標，並把腳本的檢查邏輯塞回 step

```md
4. DELEGATE 執行 `uv run scripts/check_error_codes.py --strict <路徑>`，逐條檢查每個錯誤碼是否有 HTTP 狀態與重試建議。
```

# Rule 5 - 腳本路徑只在第一次出現時寫出

- Level: `MUST`
- 腳本的完整路徑只在 SOP 中第一次 `DELEGATE` 它時寫出
- 同一支腳本在後續 step 再次出現時，以腳本名稱指明，不再寫路徑

## Good Example

- 路徑只出現一次，後續 step 以「check_error_codes 腳本」稱呼

```md
4. DELEGATE 依腳本執行規範執行 `scripts/check_error_codes.py`，傳入錯誤碼文件路徑，取回缺漏清單。
5. WRITE 依缺漏清單補正錯誤碼文件。

## Phase 3 -- 完成核對

1. DELEGATE 依腳本執行規範再次執行 check_error_codes 腳本，傳入補正後的錯誤碼文件路徑，取回缺漏清單；清單為空才算完成。
```

## Bad Example

- 後續 step 又寫了一次路徑

```md
1. DELEGATE 依腳本執行規範執行 `scripts/check_error_codes.py`，傳入補正後的錯誤碼文件路徑，取回缺漏清單；清單為空才算完成。
```

# Rule 6 - 更新既有的規範引用

- Level: `MUST`
- 目標 skill 因為多了腳本執行規範而有多份 RuleFile 時，SOP 中原本只寫「依規範」的 step，必須改為指明是哪一份規範
- 既有的 `READ` step 若沒有寫明規範名稱，必須補上「將其視為唯一 <規範名稱> 規範來源」

## Good Example

- Before：skill 只有一份 RuleFile，只寫「依規範」

```md
1. READ 讀取 `rules/錯誤碼-格式規範.md`，將其視為唯一規範來源。
2. WRITE 依規範撰寫錯誤碼文件。
```

- After：加入腳本執行規範後，指明是錯誤碼規範

```md
1. READ 讀取 `rules/錯誤碼-格式規範.md`，將其視為唯一錯誤碼規範來源。
2. WRITE 依錯誤碼規範撰寫錯誤碼文件。
```

## Bad Example

- 已經有兩份 RuleFile，仍只寫「依規範」，無法判斷依據哪一份

```md
2. WRITE 依規範撰寫錯誤碼文件。
```

# Rule 7 - 第一次展開時補上 `compatibility`

- Level: `SHOULD`
- 目標 skill 第一次有腳本時，在 SKILL.md 的 frontmatter 補上 `compatibility`，寫明需要 uv 與 Python 版本下限，不超過 500 字元
- Python 版本下限涵蓋所有腳本的 `requires-python`；已有 `compatibility` 時，核對是否仍然涵蓋
- `compatibility` 不列出各腳本的第三方套件，套件只寫在各腳本的 PEP 723 區塊

## Good Example

- 寫明 uv 與 Python 版本，套件宣告留在腳本裡

```md
---
name: skill-api-doc
description: 當要撰寫 API 錯誤碼文件時使用。
compatibility: 需要 uv 與 Python 3.11 以上,各腳本的第三方套件宣告在 scripts/*.py 開頭的 PEP 723 區塊
---
```

## Bad Example

- 把第三方套件也列在 frontmatter，與腳本裡的 PEP 723 區塊變成兩份來源，日後容易不一致

```md
---
name: skill-api-doc
description: 當要撰寫 API 錯誤碼文件時使用。
compatibility: 需要 uv、Python 3.11 以上、pyyaml、requests
---
```
